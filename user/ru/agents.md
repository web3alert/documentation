# Для агентов

В каталоге Web3alert есть декодированные ончейн-события из сетей EVM и Substrate, включая Ethereum, Polkadot и Kusama. Агент может использовать [14 инструментов MCP](mcp-server.md#endpoint-для-агентов), чтобы найти триггер, подписаться на него и получать подходящие события в формате JSON.

## 1. Получите ключ агента

### Создайте ключ в приложении

Войдите в [Web3alert](https://web3alert.io), выберите рабочее пространство, в котором вы состоите, и создайте ключ на [странице Agents](https://web3alert.io/agents). Ключ действует с вашей ролью в этом пространстве и в пределах выданных ему прав. Скопируйте секрет при создании. Он показывается один раз.

У каждого ключа есть право `read`. Добавьте `manage`, чтобы регистрировать вебхуки, создавать подписки или запрашивать котировки для пополнения. Добавьте `spend`, чтобы покупать тарифы с баланса в EUR. Можно установить [месячный лимит расходов](limits.md#agent-payments) и срок действия 30, 90 или 365 дней. Оба ограничения необязательны.

Существующие токены сессий работают, пока сервер их не отзовёт. Для новых подключений используйте ключ агента.

### Зарегистрируйтесь с кошельком Ethereum

Агент с внешним аккаунтом Ethereum (EOA) может создать собственный аккаунт Free. Сначала запросите одноразовый nonce. Оба запроса SIWE публичные.

```http
POST /api/agent/siwe/nonce
Host: web3alert.io
```

```json
{
  "nonce": "exampleNonce123456",
  "issuedAt": "<ISO-8601 timestamp>",
  "expiresAt": "<ISO-8601 timestamp>"
}
```

Составьте сообщение EIP-4361 с полученными nonce и `issuedAt`, подставьте адрес и подпишите точный текст кошельком. Nonce действует 10 минут. Сервер проверяет, что `issuedAt` отличается от его времени не более чем на 5 минут.

```http
POST /api/agent/siwe/verify
Host: web3alert.io
Content-Type: application/json

{
  "message": "web3alert.io wants you to sign in with your Ethereum account:\n<your Ethereum address>\n\n\nURI: https://web3alert.io\nVersion: 1\nChain ID: 1\nNonce: <nonce>\nIssued At: <issuedAt>",
  "signature": "<wallet signature>"
}
```

Пример ответа `200`. Объект `key` показан в сокращённом виде.

```json
{
  "account": { "id": "<account-id>", "created": true },
  "key": { "id": "<key-id>", "scopes": ["read", "manage", "spend"] },
  "secret": "w3a_<key-secret>",
  "claimUrl": "https://web3alert.io/claim/<claim-token>"
}
```

При каждом успешном входе выдаётся новый ключ для первоначального рабочего пространства со всеми тремя правами, без лимита и срока действия. Используйте `secret` как Bearer-ключ. Проверка выдаёт ссылку для получения доступа при создании аккаунта или когда действующей ссылки нет. Если ссылка уже действует, `claimUrl` равно `null`. Когда человек привязывает к аккаунту Telegram или Google, вход с кошельком возвращает `403 account_claimed`. Попросите у этого человека ключ агента.

Передайте ссылку на получение доступа человеку, который будет управлять аккаунтом. На странице указаны кошелёк, дата создания аккаунта и срок действия ссылки, доступны кнопки входа через Telegram и Google. После входа открывается страница Agents, где можно просматривать и контролировать ключи и проверять тариф, баланс и расходы. Если логин уже привязан к другому аккаунту Web3alert, используйте другой. Последняя ссылка действует семь дней. Заменить её можно через [`POST /api/agent/claim-link`](api-account.md#post-api-agent-claim-link).

Получение доступа к аккаунту оставляет активными ранее выданные ключи кошелька. После входа проверьте ключи на [странице Agents](https://web3alert.io/agents) и отзовите ненужные.

Эндпоинты nonce и проверки SIWE используют общий лимит на IP на входном прокси — 1 запрос в секунду со всплеском до 10. При ответе `429` соблюдайте `Retry-After`. Прокси отклоняет запрос до проверки подписи и не возвращает тело с кодом `signup_limited`. Если подписанное сообщение устарело, запросите новый nonce. При ответе API `429 signup_limited` nonce уже использован. По истечении указанного времени запросите новый nonce и подпишите сообщение заново.

## 2. Подключите MCP-клиент

Используйте Streamable HTTP по адресу `https://web3alert.io/mcp/agent`. Список инструментов доступен без токена. Для вызовов передавайте `Authorization: Bearer <agent-key>`.

### Claude Code

Задайте ключ агента в переменной `WEB3ALERT_KEY` в терминале и выполните эту команду.

```bash
claude mcp add --transport http web3alert-agent https://web3alert.io/mcp/agent \
  --header "Authorization: Bearer $WEB3ALERT_KEY"
```

### Claude Desktop и Cursor

Добавьте запись в `mcpServers` в файле `claude_desktop_config.json` для Claude Desktop (Settings → Developer → Edit Config) или в личном файле `~/.cursor/mcp.json` для Cursor. В примере используется мост `mcp-remote`, который запускается через `npx`. Замените пример ключа своим значением.

```json
{
  "mcpServers": {
    "web3alert-agent": {
      "command": "npx",
      "args": [
        "-y",
        "mcp-remote",
        "https://web3alert.io/mcp/agent",
        "--header",
        "Authorization:${AUTH_HEADER}"
      ],
      "env": {
        "AUTH_HEADER": "Bearer YOUR_AGENT_KEY"
      }
    }
  }
}
```

### VS Code

Для подключения через редактор добавьте запись в `servers` в файле `.vscode/mcp.json` и передайте переменную `WEB3ALERT_KEY` в окружение процесса VS Code.

```json
{
  "servers": {
    "web3alert-agent": {
      "type": "http",
      "url": "https://web3alert.io/mcp/agent",
      "headers": {
        "Authorization": "Bearer ${env:WEB3ALERT_KEY}"
      }
    }
  }
}
```

## 3. Пополните баланс и купите тариф

Перед оплатой убедитесь, что у ключа есть право `spend`. Проверьте в приложении или уточните у владельца аккаунта, что нет незавершённого оформления тарифа или действующего тарифа с автопродлением. Если оплачиваете доступ к входящим событиям, проверьте тариф владельца пространства. Покупка тарифа в другом аккаунте не меняет доступ к входящим событиям владельца.

1. До подписания вызовите `get_account({})`. Проверьте баланс в EUR и убедитесь, что покупка укладывается в остаток месячного лимита ключа, если он задан. Новый аккаунт начинает с 0 €, месяц Advanced стоит 15 €. Для этого примера с нулевым балансом вызовите `get_topup_requirements({"amountEur":15})` с правом `manage`. Пополнение возможно на сумму от 5 до 500 €. Web3alert применяет справочный курс ЕЦБ для USD, считает 1 USDC равным 1 USD и не добавляет наценку.
2. Запросите новую котировку. Отправьте то же тело без подписи платежа на `https://web3alert.io/api/billing/wallet/x402-topup` по HTTPS. Перед подписью убедитесь, что URL платежа в точности совпадает с этим адресом, сеть — Base (`eip155:8453`), актив — USDC (`0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`), а `payTo` совпадает с адресом в новой котировке. Проверьте ожидаемую сумму в USDC. Суммы передаются строками в атомарных единицах с шестью знаками после запятой. Например, `"1000000"` — это 1 USDC. Остановитесь, если проверка не пройдена. Подпишите эту котировку своим клиентом x402 v2 и кошельком. Отправляйте тело запроса методом `POST` с Bearer-ключом и подписью в `PAYMENT-SIGNATURE` только на этот URL. Отключите перенаправления для подписанного `POST`.
3. При ответе `202` или `5xx` либо при тайм-ауте подписанного `POST` считайте результат платежа неизвестным. Повторяйте запрос ограниченное число раз с тем же телом и подписью в том же пространстве, даже после истечения котировки. Если результат всё ещё неизвестен, остановитесь и сохраните доступные идентификаторы, например `topupId`, для сверки оператором. Пока результат не подтверждён, не подписывайте другой платёж для той же цели. Перед покупкой дождитесь расчёта по [пополнению](api-billing.md#post-api-billing-wallet-x402-topup) и зачисления на баланс.
4. Сгенерируйте новый `requestId` для покупки, например UUID, и подставьте его вместо `<new-uuid>` в `buy_plan({"planId":"advanced","durationMonths":1,"requestId":"<new-uuid>"})`. Нужно право `spend` и достаточный баланс в EUR. Advanced или Pro можно купить на 1, 3, 6 или 12 месяцев без автопродления. Используйте тот же ID и параметры только при повторе этой покупки. Действующий тариф с автопродлением даёт `key_not_allowed`. Незавершённое оформление или действующий более высокий тариф могут заблокировать покупку с `api_error` и сообщением API. Попросите владельца сначала решить вопрос с текущим тарифом или оформлением.

## 4. Создайте первую подписку

Выберите публичный HTTPS-вебхук или, на Advanced и Pro, входящие события рабочего пространства (inbox). Для добавления вебхука, создания подписки, чтения входящих событий и истории доставок нужна роль `owner` или `admin`.

Указывайте уникальный `title` для каждой новой подписки через `create_subscription`. Если ответа нет, вызовите `list_subscriptions` и поищите подписку по названию перед повтором. Если по названию результат неясен, проверьте правила и действия из [GET /api/subscriptions](api-subscriptions.md#get-api-subscriptions). Остановитесь, если всё ещё неясно, была ли создана подписка.

### Доставка на вебхук

В этом примере заменяйте значения в угловых скобках результатами предыдущих вызовов. Вместо адреса из примера укажите HTTPS-адрес своего вебхука без имени пользователя и пароля. Выберите событийный триггер и передайте обязательные `inputs`, которые покажет `get_trigger`. В примере у триггера нет обязательных входных параметров.

1. `get_account({})` → Аккаунт, тариф, текущий воркспейс, баланс кошелька в EUR, лимиты тарифа и счётчики подписок, если они доступны.
2. `find_triggers({"kind":"event","limit":5})` → Подходящие триггеры из опубликованного каталога и текущего воркспейса, включая `fullname` каждого триггера.
3. `get_trigger({"trigger":"<trigger-fullname>"})` → Входные параметры триггера, поля события и поля для фильтрации.
4. `add_webhook({"name":"agent-events","url":"https://example.com/webhooks/web3alert"})` → `fullname`, имя и URL зарегистрированного вебхука. Секрет подписи доступен только в ответе `add_webhook` в поле `signingSecret`. Если заменить его позже, секрет изменится для всех получателей этого эндпоинта. Сохраните секрет для принимающей стороны.
5. `create_subscription({"trigger":"<trigger-fullname>","webhook":"<webhook-fullname>","title":"<unique-title>","state":"on"})` → ID, название, итоговое состояние, триггер и вебхук подписки.
6. `get_delivery_log({"subscriptionId":"<subscription-id>"})` → Результаты доставки и `nextCursor`, если есть ещё результаты. Для истории оповещений используется тариф первого аккаунта с ролью владельца в списке доступа воркспейса. Если такого аккаунта нет, API проверяет тариф аккаунта, который сделал запрос. Если в тариф не входит история, инструмент возвращает `not_in_plan`.

   Если курсор не может продвинуться из-за того, что у 500 или более доставок одна и та же отметка времени, инструмент возвращает `api_error`. Уточните фильтр, например по статусу, и начните заново без курсора.

Убедитесь, что подписка вернулась со значением `state` равным `on`. После этого вебхук может получать подходящие события. Укажите новое имя вебхука или найдите уже зарегистрированный вебхук с помощью `list_webhooks`.

### Тело запроса вебхука

Ваш вебхук получает тело в формате JSON с ID события. Новые вебхуки получают подписанные доставки, и Web3alert автоматически повторяет попытки при сбоях, для которых предусмотрен повтор. Формат тела, проверка подписей, повторы и устранение дублей описаны в разделе [Вебхуки](webhooks.md).

### Доставка во входящие события

Найдите триггер, проверьте его параметры через `get_trigger` и вызовите `create_subscription({"trigger":"<trigger-fullname>","inbox":true,"title":"<unique-title>","state":"on"})`. Передайте обязательные `inputs`. Инструмент принимает один способ доставки за вызов и создаёт или переиспользует inbox рабочего пространства.

Вызовите `read_events({})`, чтобы начать с самого старого сохранённого события. Читайте дальше, пока `hasMore` равно `true`, и передавайте непустой `nextCursor` как `after` в том же пространстве. `gap: true` означает, что ранее сохранённые события отсутствуют до первого результата после курсора или между результатами на той же странице. Пустая страница тоже может показать пропуск, если более новые сохранённые события больше недоступны. Недоставленные события смотрите через `get_delivery_log`, когда доступна история доставки. Для дедупликации используйте `id`.

Тариф владельца пространства определяет, сохраняются ли события и как долго они хранятся. Если владельца нет, для хранения используется тариф создателя подписки. Advanced хранит до **7 дней или 25 000 событий**, Pro — до **30 дней или 100 000 событий**. Тариф без истории оповещений не сохраняет события. Создание и чтение inbox проверяют тариф владельца пространства, а при его отсутствии — тариф вызывающего аккаунта, и возвращают `not_in_plan`, если в этот тариф не входит история.

Когда применимый тариф не включает историю оповещений, API отклоняет запись во входящие события. Эти события не появляются ни в `read_events`, ни в журнале доставки. После пяти подряд недоставленных в этот канал событий подписка блокируется. Для возобновления доставки восстановите платный тариф владельца пространства или создателя подписки, если владельца нет. Проверьте состояние через `list_subscriptions` и вызовите `set_subscription_state` с `state: "on"` для заблокированных подписок. Убедитесь, что ответ содержит `on`. Возобновляется доставка только будущих событий.

## 5. Соберите триггер

На Advanced или Pro подключите клиент к `https://web3alert.io/mcp/agent/build` с тем же заголовком Bearer. Сервер генерирует триггер из ABI контракта EVM, IDL Solana или метаданных Substrate без написания кода.

1. Вызовите `find_contract` для сети платформы и укажите адрес контракта, программу Solana или паллет Substrate. В `chain` передайте короткое имя, например `ethereum`, `base`, `arbitrum-one`, `polkadot` или `solana`, либо имя в формате `common.<chain>` или `common.source.<chain>`. Если сеть неизвестна, ищите доступные имена после `Supported:` в сообщении об ошибке.

   Для EVM поле `recentBlocks` показывает, сколько недавних блоков охватывает `recentCount` каждого события, максимум 1 000. Диапазон может быть меньше, если провайдер отклонит широкий запрос. Значение `null` означает, что прочитать блоки не удалось.
2. Передайте ту же сеть и цель вместе с точной сигнатурой события в `plan_trigger`. Сохраните `draftId`. Черновик действует семь дней.
3. Вызовите `test_trigger` для черновика. Сервер может найти недавний пример, также можно указать блок или слот. Продолжайте после результата `matched` в последнем тесте.

   Поиск проверяет до 12 недавних слотов для Solana и до 12 недавних блоков для Substrate. Если в EVM уже прочитан хотя бы один диапазон логов без совпадений, ответ провайдера с ошибкой, включая тайм-аут на его стороне, или отказ среды выполнения без конкретной причины для более старого диапазона может завершить поиск с `no_match`. Этот результат охватывает только прочитанные диапазоны. Ошибки транспорта, истечение срока поиска и невозможность прочитать хотя бы один диапазон дают `retryable`.

   Если известно, где произошло событие, или нужно пропустить поиск, передайте его `slot` для Solana или `block` для EVM или Substrate в `test_trigger`.

4. Вызовите `activate_trigger` с `draftId` и своим `requestId`. Повторяйте запрос с тем же ID. Триггер сохраняется в приватном проекте агента в рабочем пространстве. Участник пространства с ролью `developer` может собрать и активировать триггер. Использовать полученное полное имя в `create_subscription` может только `owner` или `admin`. Если проект агента в пространстве создал другой участник, при активации учитывается тариф создателя проекта для проверки единиц триггеров. Если этот тариф больше не разрешает управление триггерами, возвращается `plan_required`.

Для `find_contract` и `test_trigger` нужно право `read`, для планирования и активации — `manage`. См. [справочник инструментов сборки](mcp-server.md#build-endpoint).

## Лимиты

На тарифе Free аккаунт может иметь **до 5 созданных им активных подписок на проекты без статуса Free** суммарно во всех воркспейсах. Подписки на проекты Free не входят в лимит.

На тарифе Free для подписок с доставкой только на встроенные вебхуки по умолчанию действуют всплеск до 12 оповещений, постоянная скорость 1 оповещение в секунду и предел очереди в 15. Эти подписки не расходуют квоту доставки воркспейса.

Тариф Free позволяет делать 60 запросов в минуту к внешнему API. Тесты подписок и история оповещений доступны на тарифах Advanced и Pro. В обоих случаях API проверяет тариф первого владельца воркспейса и использует правило из шага 6, если владельца нет. Полные таблицы доступны в разделе [«Лимиты»](limits.md).

По умолчанию сервер MCP разрешает 120 вызовов инструментов на аккаунт в минуту. Все три эндпоинта используют общий лимит в каждом серверном процессе. `get_account` возвращает тариф аккаунта и те же [лимиты тарифа](api-account.md#me-limits), что и `GET /api/me`. Поле `limits` в ответе инструмента равно `null`, если API не передаёт лимиты тарифа. MCP может использовать сохранённый ответ `/me` до 30 секунд, поэтому смена тарифа может отразиться в `get_account` с такой задержкой.
